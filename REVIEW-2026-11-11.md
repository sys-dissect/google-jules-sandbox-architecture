# Final Comprehensive Review — google-jules-sandbox-architecture

## 1. Verdict

The repository provides an incredibly detailed, largely accurate, and extremely well-documented account of the Jules sandbox environment, suitable for publication with a few targeted corrections. The single weakest area is the cross-document consistency regarding the orchestrator control plane: PR #18 correctly overturned the initial VSOCK assumption (proving the connection is TCP over virtio-net), but several Tier-1/Tier-2 documents (`ARCHITECTURE.md` and `README.md`) still assert the old VSOCK bridge model as fact. While the evidence collection is robust and reproducible, the narrative synthesis requires a final reconciliation pass to align early assertions with the later empirical findings.

## 4. Findings

### Critical

*   **Severity:** Critical
*   **File(s) / Line(s):** `ARCHITECTURE.md` (Layer 3), `README.md`, `SYSTEMD_AND_HARNESS_IPC.md`, `FIRECRACKER_AND_VSOCK.md`, `OPT_AND_HARNESS.md`, `TASK_LIFECYCLE.md`
*   **Claim:** The orchestrator control plane uses AF_VSOCK (e.g., "AF_VSOCK-based hypervisor-to-guest orchestration, socat-bridged SSH ingress").
*   **Evidence shows:** `evidence/GUEST_HOST_COMMS.md` correctly proved the orchestrator uses TCP over virtio-net (`192.168.0.1 -> 192.168.0.2:22`), and the VSOCK bridge (`socat VSOCK-LISTEN:22`) is completely idle.
*   **Live VM showed:** `ss -tanp` confirms established TCP connections from `192.168.0.1` (high ports) to local port `22` (sshd). `ss -xlpn` shows the VSOCK bridge listening but with 0 established connections. *Contradicted.*
*   **Fix:** Completely rewrite Layer 3 in `ARCHITECTURE.md` to remove the VSOCK assertion and document the TCP over virtio-net ingress. Remove or heavily caveat the VSOCK bridge mentions in all other referenced files.

### High

*   **Severity:** High
*   **File(s) / Line(s):** `AUTH_AND_BOOT_SURFACE.md` (and implied in other early docs)
*   **Claim:** Jules boots in "sub-second" time.
*   **Evidence shows:** `CHECKPOINT_FINDINGS.md` and `systemd-analyze` show ~3.0s kernel + ~18.2s userspace (21.2s to graphical target).
*   **Live VM showed:** `journalctl -b` confirms `Startup finished in 613ms`, but `sshd` did not actually accept the first orchestrator connection until slightly later. The full userspace takes significantly longer than sub-second. *Contradicted.*
*   **Fix:** Remove all remaining references to "sub-second" boot times across all documents, replacing them with the accurate ~21.2s measurement.

*   **Severity:** High
*   **File(s) / Line(s):** `evidence/raw/task4_limits_*/net_burst_250mb.txt`
*   **Claim:** Network burst test downloaded 250MB. (Implied by filename and test description in `scripts/probe_task4_limits.sh`).
*   **Evidence shows:** The files `net_burst_250mb.txt` in both standard and OOM drops explicitly show `size_download=1` byte.
*   **Live VM showed:** Re-running the curl command yields similar results (1 byte downloaded or immediate exit). *Contradicted (the measurement is invalid).*
*   **Fix:** Explicitly state in the docs that the network burst test failed to measure actual throughput because the endpoint rejected the request, and the 250MB/s figure is unmeasured.

*   **Severity:** High
*   **File(s) / Line(s):** `scripts/probe_task1_harness_recorder.sh`
*   **Claim:** Collects process environments.
*   **Evidence shows:** The script contains `sudo cat "/proc/$pid/environ" 2>/dev/null | tr '\0' '\n' > "$OUT_DIR/proc_${pid}_environ.txt"`. This is highly risky.
*   **Live VM showed:** The script runs this exactly as written, meaning if a credential exists in the environment of `sshd` or `tmux` (like `TAILCAT_PEER_KEY`), it will be written to disk.
*   **Fix:** Modify `probe_task1_harness_recorder.sh` to redact or hash the environment variables before writing to disk, similar to the pattern in PR #18's `sensitive_inventory.txt`.

### Medium

*   **Severity:** Medium

*   **Claim:** Option A is "Native Ext4 Snapshotting" and Option B is "VFS Storage Driver".
*   **Evidence shows:** The evidence in `CONTAINERD_DOCKER_RUNTIME.md` explicitly shows that nesting OverlayFS inside OverlayFS fails with `EINVAL`, necessitating the VFS storage driver workaround (Option B).
*   **Live VM showed:** Live Docker info confirms `Storage Driver: overlayfs` with `io.containerd.snapshotter.v1`.
*   **Fix:** Clarify in `REPRODUCE.md` which option actually matches the observed Jules environment.

*   **Severity:** Medium

*   **Live VM showed:** `nmap -sn 192.168.0.0/24` reveals only `.1` (gateway) and `.2` (guest). *Reproduced.*
*   **Fix:** Add a note acknowledging the `/24` ping sweep is a boundary edge-case, though it successfully confirmed no other tenants were on the subnet.

*   **Severity:** Medium
